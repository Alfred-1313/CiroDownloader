# Project working rules

- Publish authorized changes to GitHub. Do not connect to, deploy to, or change the user's server unless the user explicitly requests deployment again.
- Bot UI is Persian. Prefer clear bold headings and blockquotes in default messages. Installer output stays English.
- Personalization follows the owner's `Skill-UI-UX` (telegram-bot-customization): one main screen of white title buttons that only explain themselves (`custom:hint:<id>` answers with a short alert from a `hint_*` text and must not cancel pending input), one entry per screen below each title, ✏️/🔘 markers for customised items, a per-item screen with state, default text, edit and reset, one-tap switches on the features page, reset-all with confirmation and a close button. One colour rule on every Personalization screen (`Personalization::recolor`): titles are always white, every other tappable button is blue (`primary`), never green or red; a switch shows its state as ✅/❌ in its text; only the colour picker keeps its own colours. The features page stays short: the 18+ site has its own page (`custom:adultpage`). Keep this structure for future additions; long screens are paged and Back returns to the same page.
- Accepted media requests react to the original user's link message with 👾 by default. Keep the reaction configurable or disabled in Personalization, apply it only after the job/status is ready, and make reaction rejection or transport failure optional with a short timeout so media processing continues.
- New services follow the Instagram flow unless the user explicitly asks for YouTube-style quality selection. Pinterest uses gallery-dl for single pins and validated pin.it redirects; reject boards/profiles, keep ordered visual items separate from story music/text assets, and retain per-service cookies, captions, source visibility and article settings. Share conversion, cookie panels and carousel code while preserving existing Instagram sessions. Exclude all temporary gallery page caches from backups.
- TikTok and X use the same direct gallery flow with separate sessions and settings. TikTok short links may follow only bounded TikTok short-link hops to one validated post; keep up to 35 ordered photos, excluding standalone music and covers. X accepts x.com/twitter.com post links, uses x.com auth_token cookies, and returns only the requested post's native media, without quoted posts or conversation expansion. Keep service-bound callback prefixes and per-service item limits in the shared registry.
- Spotify accepts one `open.spotify.com/track/ID` link, never albums, playlists or short links. It reads the public track page, never Spotify's protected audio, finds the matching YouTube recording by length and name (SoundCloud with a stricter name-and-artist match when YouTube refuses the server), and sends one tagged MP3 in the media lane with the usual single status message. It needs no Spotify cookies. Its texts, caption and source button (default off, no link in the default caption) live in a Personalization screen under the music heading.
- SoundCloud accepts one public track (`soundcloud.com/ARTIST/TRACK` or an `on.soundcloud.com` share link followed through at most three validated hops), never sets, profiles or private tracks. It downloads the full track with yt-dlp, never a 30 s preview, needs no cookies and follows the Spotify flow, texts and screens. Music links react with their own Personalization choice (default 🔥, because Telegram offers bots no music reaction); turning reactions off turns them off for music too. Keep music service callback prefixes in the shared registry.
- Links to a Spotify artist, album or playlist, a SoundCloud profile or set, or a Deezer artist open one music menu in the job's status message instead of a download: a photo (artist picture, then each album's own cover via editMessageMedia) when there is a trusted image, otherwise text; tabs with counts, eight items per page, white page title, green current tab, red Back and Close, owner/chat/topic-bound `mm:ID:OP` callbacks, 24-hour expiry. Spotify's embed pages give popular tracks, album/playlist tracks and pictures; Deezer's public API, then Apple's iTunes Search API, give the rest of an artist's catalogue, accepted only when the artist's own popular tracks match by title and length. Never call Spotify's API with the token embedded in its pages. A tapped track is queued like a pasted link without the cooldown; by default the menu message becomes its status and is deleted after the audio (a Personalization switch keeps menus open). Lists of tracks offer download all (up to 50): one `batch` job on the menu's own message prepares tracks in a pool (`MUSIC_PARALLEL`, unset = sized to the container's cgroup CPU and memory, 2 to 6, three for compose's 1 CPU / 768 MB; a freed slot starts the next track at once) in `storage/music-batches` (never in backups); its progress refreshes itself every few seconds with the elapsed time, the tracks in work and the failed tracks with what each source said (also pushed to `recent_errors` as `batch`); a track failed for a passing reason (network, process) is retried once; unless YouTube's state is known from the last 15 minutes one light probe runs first; after a YouTube bot-check refusal every Spotify source asks SoundCloud first for 15 minutes (`storage/.youtube-blocked`/`.youtube-ok`, never in backups; YouTube still second, a YouTube success clears it); yt-dlp keeps a private cache in `storage/yt-cache` (never in backups, pruned after a week) instead of `--no-cache-dir`; Spotify-source matching also compares consonant skeletons so transliterations and Persian script match (names of at least four consonants, artists of three), then sends every track (or size-limited stored ZIP document) as its own message in order, never as a Telegram album, because Telegram shows no buttons under album messages; each track has its own caption (`batch_caption`: artist and title in bold, an empty line, its length in a quote; ZIPs keep the album in bold and a collapsed quote of names, never failures) and, when the bot's inline mode is on (getMe `supports_inline_queries`, checked every ten minutes), a `📤` share button (`switch_inline_query_chosen_chat` limited to user and group chats, query `s:` plus a random 16-character token in `shares`, answered for anyone with `InlineQueryResultCachedAudio`, 90 days; `inline_query` is in the poller's allowed updates); only the last carries the red `🔙` back button, usable only by the requester; the old menu message is deleted, and the button deletes the sent messages and brings the menu back as a new message. Next to download all, a blue choose-tracks button (`m`/`k`/`d` ops, `view.pick`, up to 50, owner only) turns tracks into toggles (chosen = blue + ✅) with a green send-chosen (N) and a red cancel; it queues the same batch with only those tracks in list order; leaving the list forgets the choice. Deliveries are paced (≈1 s private, ≈3 s groups, `Config::paceMessages`), `Telegram::call` waits out 429 `retry_after` (up to 90 s for sends, 20 s otherwise, four times), status edits during sending are every five seconds and never fatal, and a track Telegram still refuses ends the delivery with what arrived plus the back button on the last of them. Singles (opened from the singles tab) offer no download all. A track tapped in a menu that closes on choice carries the same caption and share button as a track of an album, plus the red back button on the audio itself; single-track links use the same caption and share button; the owner-only stop sends nothing and brings the menu back with a green continue button. Music keeps AAC/MP3 sources as they are (M4A or MP3, no re-encoding; Opus becomes 160 kbps MP3) unless the administrator switches to always MP3. Button colours: green starts a download, red goes back or stops; every user-facing back button uses 🔙. SoundCloud tracks whose file cannot be taken (DRM, preview, refused) go through the Spotify sources in the same order (YouTube, then another SoundCloud upload, never the locked original). Cookie imports without the service's sign-in cookies are marked as guest cookies. All menu texts and buttons are `audience: user` Personalization entries under the music heading.
- `/music ARTIST-TITLE` and `/spotify NAME` (private and group, `MusicSearch`) search without a link: a search is queued as `https://open.spotify.com/search/QUERY/tracks|artists` (`searchAddress`/`collectionUrl`, query 2 to 80 characters, `searchQuery`) so it uses the normal intake, cooldown, reaction and one status message that becomes the result menu (`MusicMenu::open`, service `search`). `/music` lists up to 16 songs from Deezer (exact artist-and-title query first, then the words loosely) and Apple's iTunes, de-duplicated and ranked, with SoundCloud search added only when they know almost nothing (other alphabets); tapping a song queues it like a menu track (details-based `spotify` phase, or the SoundCloud address), and the list offers no download all or choose-tracks. `/spotify` resolves a name without Spotify's protected token: Deezer artist search (exact name, else every word; most fans wins), then MusicBrainz (public, one request a second, identified User-Agent) whose Spotify link is trusted only when the same page names the same Deezer artist (or is the single exact name when Deezer found none); a Spotify link opens the normal Spotify artist menu, otherwise (or when its page cannot be read) the Deezer artist, then the best Apple artist. A search with no result says so plainly (`search_empty`, not an error); every catalogue failing is the usual retry notice. Without text each command answers with its usage text. Telegram's `/` menu for everyone (`setMyCommands` default scope, `MusicSearch::register`: start, help, music, spotify; resent only when it changes, retried at most hourly) and the administrators' own menu (which repeats the two search commands) come from `command_*` texts. All its texts are `audience: user` Personalization entries under the music heading (`search` screen). Details: `docs/music-search.md`.
- Video chats and live streams cannot be joined, started or heard by a bot (the Bot API has only the service messages and the `can_manage_video_chats` right, with no method). `VideoChats` passes the news on: a `video_chat_started`/`video_chat_ended` service message from a channel (`channel_post`, requested by the poller) or from a group, only when a bot administrator started the group's video chat, becomes one private `admin` message to every administrator (`Store::administratorIds`, bootstrap-rooted); no post text is read or kept and channel updates are logged by field name at most every ten minutes. A live radio over RTMP needs a person to start the stream in the app (data sent alone starts nothing and gives no error). Details: `docs/video-chats.md`.
- The live radio (`Radio`, `RadioPanel`, `bin/radio.php` supervisor with `bin/radio-player.php` and `bin/radio-prepare.php`; compose service `radio` in profile `radio`, `RADIO_STATIONS` default 3, at most 6) plays a chat's queue into its live stream over RTMP. A bot cannot start or join a live stream and data sent alone starts nothing and gives no error, so a person starts the stream in the app and gives the bot its address and key once, privately (`/radio` in a private chat lists chats where `VideoChats` saw a stream start and the person may manage; the message with the key is deleted at once). The address and key are the only secret: a 0600 file `storage/radio/keys/CHAT`, never in the database, a log (ffmpeg output is redacted), a backup (`./radio` is excluded) or a test (tests use a made-up key). The stream is live or not from the start/end service messages. Songs queue through `rd:p:TOKEN` (the ▶️ under a sent song, via `radio_picks`), `mm:ID:y` (play all in any list of several songs: albums, EPs, playlists, sets, popular tabs, search results) and `mm:ID:y:p` (play chosen); preparation reuses the music download sources (`Worker::radioAudio`), three songs ahead, two at a time. One ffmpeg output per session, sound written two seconds ahead of the clock (no -re) so a hiccup never empties it, the next decoder and its cover started ahead and the leftover of a block carried over so there is no gap; silence while the next song is prepared; the picture is the cover of the song playing (saved by the preparer, fitted into 640×360 on a dark background), sent as JPEG frames on a second pipe by the clock (wall-clock stamps), switched when the clock reaches the point of the sound where its song begins, and never blocking the sound; a player asked to stop exits at once (children inherit the supervisor's lock); the session ends one minute after the queue empties, when the stream ends, on stop, or when the output fails three times (the song stays queued and its adder is told). Who may use it: the administrators of that chat (`getChatMember`, cached two minutes) and of the bot, or with `radio.access=bot` only the bot's administrators; `radio.enabled` switches the whole radio off (buttons hidden, players stopped). Both are switches on the features page (admin texts); every radio text and button is an `audience: user` Personalization entry (`radio` screen). Details: `docs/radio.md`.
- Pornhub (`pornhubUrl`: one `view_video.php?viewkey=` or `/embed/` page on pornhub.com and its www/m/language subdomains, canonical `https://www.pornhub.com/view_video.php?viewkey=KEY`) follows the YouTube flow (the page's picture is written by the same yt-dlp request and uploaded as a file with `editMessageMedia` `attach://`, its file ID kept as the job's poster; quality menu 240/360/480/720/1080 as offered plus the audio button from the smallest stream; same status message) but is off by default (`adult.pornhub`), works in private chats and in groups (group use on; `GroupSupport` accepts it; never in `mediaUrl`), administrators only by default (`adult.admins_only`), gated in the bot (`Bot::adultAllowed`) and again in the worker; two deletion filters, `adult.delete_private` and `adult.delete_group` (both on by default, switches on the features page, delay `adult.delete_seconds` 10/30/60/180, default 10), make the bot delete the sent video/audio message itself after the delay through `TimedDeletes` (rows in `timed_deletes`, restart-safe, swept by a short-lived worker child, retried five times, 404/403/400 forgotten) and say so at the very top of the caption (`pornhub_notice`: a quote that gives the seconds and tells the person to keep the video in their Saved Messages, then one empty line, then the rest of the caption; the `{notice}` variable of `pornhub_caption` is that block with its empty line, or empty when the filter is off). Every later 18+ site must use exactly this caption structure and the same two filters; anyone not allowed gets the ordinary `invalid` text. It is read without YouTube cookies (social proxy when set), qualities above the upload limit (stated or estimated size) are never offered, HLS streams with a known H.264 codec are listed before the plain MP4 of the same height (the CDN throttles the MP4 to ≈500 KB/s; HLS downloads eight pieces at once), and its own `pornhub_caption` (title in bold, people = the page's `cast` else the channel, length, quality, views, categories and tags as hashtags in a collapsed quote, cut to 1024) has no link or button; yt-dlp is installed with the `curl-cffi` extra so extractors that ask for browser impersonation (Pornhub answers a plain client from a cloud IP with `410 Gone`) get it; its failures carry a one-word cause (`Download::siteCause`: certificate, dns, refused, unreachable, reset, timeout, region, ratelimit, forbidden, gone, unavailable, redirect, page) as `[pornhub=cause]`, shown to administrators in the status message and `recent_errors`, never raw output; file sizes are judged by stated size, bitrate, or the bitrate in the file name (`480P_2000K_`). The switches (Pornhub, administrators only, the two deletion filters, the delay) live on the 18+ page under the features page; texts on the `pornhub` screen. A refused link is explained only to a bot administrator (`Bot::adultHint`: switch off, or group use off), in the same chat in private and by private message for a group; everyone else gets nothing about the site. The site's own trailer is not on its video page (previews exist only for related videos, with signed links), so there is no trailer download.
- Register UI messages, captions, buttons, and update notifications in `resources/ui.json` with an explicit `audience` of `user` or `admin`. Use `Ui` in PHP and the shared catalog in the host updater. Do not introduce hardcoded product strings in handlers.
- Personalization exposes only active UI fields ordinary users see. Every new user-facing feature must add its messages, captions and buttons to Personalization with `audience: user`. Administrator-only panels, status, cookies, updater and editor controls use `audience: admin` and must not be editable through lists, callbacks, legacy routes or saved edit sessions. Keep user-facing access notices editable even though administrators configure them.
- User buttons support title, semantic color and `icon_custom_emoji_id`; user texts and captions preserve native Telegram entities and supported HTML. Keep deprecated UI fields hidden from the editor while retaining compatibility where needed.
- Premium custom emoji depend on Telegram account eligibility. Preview edits before committing them, and retain working settings when Telegram rejects a preview.
- Preserve one status message across inspection, quality selection, download, upload, and errors. YouTube downloads require the authenticated owner's offered-quality selection. Instagram single files download automatically; carousels use one media message edited in place with owner/chat/topic-bound Previous/Next buttons, wide neutral defaults and no counter button. Personalization controls visibility of the Instagram source button for both single media and carousels. Persist the current slide and a navigation revision, queue edits through the bounded media lane, reject duplicate/stale callbacks, and reuse confirmed Telegram file IDs. Keep private prepared media for 24 hours so Previous works even on the last slide; clean expired or failed sessions. Personalization may select ordered Telegraph articles instead, with public media hosted on Catbox or Qu.ax and a retained result message. Only an explicit Catbox 412 rejection enables fallback hosting; never retry an uncertain upload. Keep Instagram cookies independent and private, and expose all public Instagram/article UI through Personalization.
- Administrators get status reports from the existing `/health` message: its inline buttons open statistics, services, cookies, recent errors, server and speed screens (`rp:SCREEN`, admin-only, private-only, edited in place, always Refresh/Back/Close) in the update-screen structure (blockquote title, `➖` state lines, one quote). Every finished request is counted per day and service in `stats` (90 days; plain YouTube quality inspections are not results) and the last ten failures keep only service, short reason and clean source list in `recent_errors`; never store links, usernames or raw downloader output. The speed screen (`rp:speed`) shows only numbers kept by `Store::pushSpeed` (the last ten delivered files of each service over half a megabyte: service, bytes, prepare and upload milliseconds): the main screen gives the total and one line per service with data, `rp:speed:SERVICE` lists that service's ten files with size, time and speed of download and upload, and both name the bottleneck. Every delivery path reports: video/audio (YouTube, Pornhub), single tracks, download all (`batch`), single gallery files, a carousel's first page (all slides downloaded, one uploaded) and its page turns (no download), and Telegraph articles (`article`, whose upload goes to the file host); a new feature that downloads or uploads files must call `Worker::noteSpeed` too. The speed overview carries no explanatory quote (the owner removed it); keep it that way. All report texts and buttons are `audience: admin`. The cookie checker runs every `cookies.check_minutes` (30/60/180/360/720/1440, default 360) with an administrator check-now control and alerts the administrators when cookies break.
- The management panel message lists every administrator command from `AdminCommands::LIST` (one tappable line each, from `admin_cmd_<name>` texts) and a short usage guide, and registers the same list as that administrator's own `/` menu (`setMyCommands`, chat scope, resent only when it changes, never blocking the panel). A new administrator command is one list entry and one `admin_cmd_*` text; ordinary users never get the list.
- Cookie settings (use mode, alerts, keep-alive, check interval, check now) are their own administrator screen and panel button (`cookie_settings`), never part of the cookie import service list. The screen is an inline message (`cs:` callbacks, admin-only, private-only, edited in place) of real controls: green/red switches, one button per check interval with the current one green, check now, Back and Close; never decorative text or reply-keyboard-only controls. Old reply labels still work and open it. Import stays per service.
- Keep `CHANGELOG.json` to a single entry: the latest version, and in it **only what that release added** (never items carried over from earlier releases: the updater announces every item of the entry, so a carried-over item is shown again at every update; several new items go in the order they were added, newest last), written for a beginner administrator (`title`, `what`, `example`, `default` on/off, `path` steps). The update screens follow the same Skill-UI-UX structure (title, state lines, quote, green start, red rollback, Back and Close) and are rendered identically by `Updates` (PHP) and the host updater (Python).
- Enforce admin-only access in message handlers, callbacks, and the worker before delivering files. Keep the restriction notice editable.
- The main administration panel replaces the home reply keyboard with its own reply controls and a return to the main menu. Keep administration tools inside that panel except for the explicitly supported group updater, and exclude administrator labels from Personalization.
- Add administrators from the private management panel by username, never by a numeric input. Cache Telegram-observed human profiles and verify the current private account before granting; unknown users must Start the bot. Bind grants to account IDs, not mutable usernames, and apply the same bootstrap-rooted grant validation in bot, worker and host updater. Instagram source buttons default off and default captions omit the original-post promotion link.
- Group use defaults on and is controlled from Personalization. Gate group requests, callbacks and worker delivery with that setting; keep administrator tools private except `/update` for configured bot administrators. Group update menus and buttons belong to their administrator, chat and topic; use inline controls and edit the same progress message through completion, including after an updater restart. A menu in another context must not redirect an active update. Group selections belong to the original sender and chat, and status/media must retain forum topic IDs. Ignore group chatter, other bots and commands addressed to another bot. Register public group text and the invitation button as user-facing UI.
- Keep README minimal. Put detailed operational explanations in focused documents.
