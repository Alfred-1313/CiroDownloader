# Project working rules

- Publish authorized changes to GitHub. Do not connect to, deploy to, or change the user's server unless the user explicitly requests deployment again.
- Bot UI is Persian. Prefer clear bold headings and blockquotes in default messages. Installer output stays English.
- Personalization follows the owner's `Skill-UI-UX` (telegram-bot-customization): one main screen of white title buttons that only explain themselves (`custom:hint:<id>` answers with a short alert from a `hint_*` text and must not cancel pending input), one entry per screen below each title, green marks and ✏️/🔘 markers for customised items, a per-item screen with state, default text, edit and reset, one-tap green/red switches on the features page, reset-all with confirmation and a close button. Keep this structure for future additions; long screens are paged and Back returns to the same page.
- Accepted media requests react to the original user's link message with 👾 by default. Keep the reaction configurable or disabled in Personalization, apply it only after the job/status is ready, and make reaction rejection or transport failure optional with a short timeout so media processing continues.
- New services follow the Instagram flow unless the user explicitly asks for YouTube-style quality selection. Pinterest uses gallery-dl for single pins and validated pin.it redirects; reject boards/profiles, keep ordered visual items separate from story music/text assets, and retain per-service cookies, captions, source visibility and article settings. Share conversion, cookie panels and carousel code while preserving existing Instagram sessions. Exclude all temporary gallery page caches from backups.
- TikTok and X use the same direct gallery flow with separate sessions and settings. TikTok short links may follow only bounded TikTok short-link hops to one validated post; keep up to 35 ordered photos, excluding standalone music and covers. X accepts x.com/twitter.com post links, uses x.com auth_token cookies, and returns only the requested post's native media, without quoted posts or conversation expansion. Keep service-bound callback prefixes and per-service item limits in the shared registry.
- Spotify accepts one `open.spotify.com/track/ID` link, never albums, playlists or short links. It reads the public track page, never Spotify's protected audio, finds the matching YouTube recording by length and name (SoundCloud with a stricter name-and-artist match when YouTube refuses the server), and sends one tagged MP3 in the media lane with the usual single status message. It needs no Spotify cookies. Its texts, caption and source button (default off, no link in the default caption) live in a Personalization screen under the music heading.
- SoundCloud accepts one public track (`soundcloud.com/ARTIST/TRACK` or an `on.soundcloud.com` share link followed through at most three validated hops), never sets, profiles or private tracks. It downloads the full track with yt-dlp, never a 30 s preview, needs no cookies and follows the Spotify flow, texts and screens. Music links react with their own Personalization choice (default 🔥, because Telegram offers bots no music reaction); turning reactions off turns them off for music too. Keep music service callback prefixes in the shared registry.
- Links to a Spotify artist, album or playlist, a SoundCloud profile or set, or a Deezer artist open one music menu in the job's status message instead of a download: a photo (artist picture, then each album's own cover via editMessageMedia) when there is a trusted image, otherwise text; tabs with counts, eight items per page, white page title, green current tab, red Back and Close, owner/chat/topic-bound `mm:ID:OP` callbacks, 24-hour expiry. Spotify's embed pages give popular tracks, album/playlist tracks and pictures; Deezer's public API, then Apple's iTunes Search API, give the rest of an artist's catalogue, accepted only when the artist's own popular tracks match by title and length. Never call Spotify's API with the token embedded in its pages. A tapped track is queued like a pasted link without the cooldown; by default the menu message becomes its status and is deleted after the audio (a Personalization switch keeps menus open). Lists of tracks offer download all (up to 50): one `batch` job on the menu's own message prepares tracks in a pool (`MUSIC_PARALLEL`, default 6, a freed slot starts the next track at once) in `storage/music-batches` (never in backups); its progress refreshes itself every few seconds with the elapsed time, the tracks in work and the names of the tracks that failed; after a YouTube bot-check refusal every Spotify source asks SoundCloud first for 15 minutes (`storage/.youtube-blocked`, never in backups; YouTube still second, a YouTube success clears it), then sends all tracks together as media groups of audio (or size-limited stored ZIP documents) with the caption on the very last item (the album in bold, an empty line, a collapsed `<blockquote expandable>` of bold track names only, cut to Telegram's limit, never failures or artists); Telegram shows no buttons under a group, so the red `🔙` back button comes in a message right under it with invisible default text (`batch_back_text`), while a lone item carries caption and button itself; the old menu message is deleted, and the button deletes the sent messages and brings the menu back as a new message. Singles (opened from the singles tab) offer no download all. A track tapped in a menu that closes on choice carries the same caption structure (the album when chosen inside one, else its own name, in bold; the track in a bold collapsed quote; no artist) and the red back button on the audio itself; single-track links use the same caption; the owner-only stop sends nothing and brings the menu back with a green continue button. Music keeps AAC/MP3 sources as they are (M4A or MP3, no re-encoding; Opus becomes 160 kbps MP3) unless the administrator switches to always MP3. Button colours: green starts a download, red goes back or stops; every user-facing back button uses 🔙. SoundCloud tracks whose file cannot be taken (DRM, preview, refused) go through the Spotify sources in the same order (YouTube, then another SoundCloud upload, never the locked original). Cookie imports without the service's sign-in cookies are marked as guest cookies. All menu texts and buttons are `audience: user` Personalization entries under the music heading.
- Register UI messages, captions, buttons, and update notifications in `resources/ui.json` with an explicit `audience` of `user` or `admin`. Use `Ui` in PHP and the shared catalog in the host updater. Do not introduce hardcoded product strings in handlers.
- Personalization exposes only active UI fields ordinary users see. Every new user-facing feature must add its messages, captions and buttons to Personalization with `audience: user`. Administrator-only panels, status, cookies, updater and editor controls use `audience: admin` and must not be editable through lists, callbacks, legacy routes or saved edit sessions. Keep user-facing access notices editable even though administrators configure them.
- User buttons support title, semantic color and `icon_custom_emoji_id`; user texts and captions preserve native Telegram entities and supported HTML. Keep deprecated UI fields hidden from the editor while retaining compatibility where needed.
- Premium custom emoji depend on Telegram account eligibility. Preview edits before committing them, and retain working settings when Telegram rejects a preview.
- Preserve one status message across inspection, quality selection, download, upload, and errors. YouTube downloads require the authenticated owner's offered-quality selection. Instagram single files download automatically; carousels use one media message edited in place with owner/chat/topic-bound Previous/Next buttons, wide neutral defaults and no counter button. Personalization controls visibility of the Instagram source button for both single media and carousels. Persist the current slide and a navigation revision, queue edits through the bounded media lane, reject duplicate/stale callbacks, and reuse confirmed Telegram file IDs. Keep private prepared media for 24 hours so Previous works even on the last slide; clean expired or failed sessions. Personalization may select ordered Telegraph articles instead, with public media hosted on Catbox or Qu.ax and a retained result message. Only an explicit Catbox 412 rejection enables fallback hosting; never retry an uncertain upload. Keep Instagram cookies independent and private, and expose all public Instagram/article UI through Personalization.
- Administrators get status reports from the existing `/health` message: its inline buttons open statistics, services, cookies, recent errors and server screens (`rp:SCREEN`, admin-only, private-only, edited in place, always Refresh/Back/Close) in the update-screen structure (blockquote title, `➖` state lines, one quote). Every finished request is counted per day and service in `stats` (90 days; plain YouTube quality inspections are not results) and the last ten failures keep only service, short reason and clean source list in `recent_errors`; never store links, usernames or raw downloader output. All report texts and buttons are `audience: admin`. The cookie checker runs every `cookies.check_minutes` (30/60/180/360/720/1440, default 360) with an administrator check-now control and alerts the administrators when cookies break.
- The management panel message lists every administrator command from `AdminCommands::LIST` (one tappable line each, from `admin_cmd_<name>` texts) and a short usage guide, and registers the same list as that administrator's own `/` menu (`setMyCommands`, chat scope, resent only when it changes, never blocking the panel). A new administrator command is one list entry and one `admin_cmd_*` text; ordinary users never get the list.
- Cookie settings (use mode, alerts, keep-alive, check interval, check now) are their own administrator screen and panel button (`cookie_settings`), never part of the cookie import service list. The screen is an inline message (`cs:` callbacks, admin-only, private-only, edited in place) of real controls: green/red switches, one button per check interval with the current one green, check now, Back and Close; never decorative text or reply-keyboard-only controls. Old reply labels still work and open it. Import stays per service.
- Keep `CHANGELOG.json` to a single entry: the latest version, written for a beginner administrator (`title`, `what`, `example`, `default` on/off, `path` steps). The update screens follow the same Skill-UI-UX structure (title, state lines, quote, green start, red rollback, Back and Close) and are rendered identically by `Updates` (PHP) and the host updater (Python).
- Enforce admin-only access in message handlers, callbacks, and the worker before delivering files. Keep the restriction notice editable.
- The main administration panel replaces the home reply keyboard with its own reply controls and a return to the main menu. Keep administration tools inside that panel except for the explicitly supported group updater, and exclude administrator labels from Personalization.
- Add administrators from the private management panel by username, never by a numeric input. Cache Telegram-observed human profiles and verify the current private account before granting; unknown users must Start the bot. Bind grants to account IDs, not mutable usernames, and apply the same bootstrap-rooted grant validation in bot, worker and host updater. Instagram source buttons default off and default captions omit the original-post promotion link.
- Group use defaults on and is controlled from Personalization. Gate group requests, callbacks and worker delivery with that setting; keep administrator tools private except `/update` for configured bot administrators. Group update menus and buttons belong to their administrator, chat and topic; use inline controls and edit the same progress message through completion, including after an updater restart. A menu in another context must not redirect an active update. Group selections belong to the original sender and chat, and status/media must retain forum topic IDs. Ignore group chatter, other bots and commands addressed to another bot. Register public group text and the invitation button as user-facing UI.
- Keep README minimal. Put detailed operational explanations in focused documents.
